## Q1：DP rank 和 TP 到底是什么？

一句话区分：**DP 是"多个引擎分活干"（切请求），TP 是"多个设备合起来干一件活"（切模型）**。

- **DP rank（数据并行序号）= 一个独立的引擎进程**。每个 DP rank 就是一个独立的 `vllm serve` 进程：自己的 API 端口、自己的调度器、自己独立服务一批请求，互相不知道对方的存在
- **TP（张量并行）= 一个 rank 内部用几张卡一起算同一个请求**。模型每层权重切成 N 份放在 N 张卡上，同一个请求过来 N 张卡各算 1/N，算完在**机内**通过 HCCL 集合通信拼接。TP 永远不出机器——跨机做 TP 会被每 step 一次的跨机 all-reduce 拖死

本集群的切法（每台 16 个逻辑设备）：

```
P 节点（如 001）：4 个 DP rank × 每个 TP4（4 设备协同）= 16 设备
  rank0 → 设备 0-3    （端口 7100，独立引擎）
  rank1 → 设备 4-7    （端口 7101，独立引擎）
  rank2 → 设备 8-11   （端口 7102，独立引擎）
  rank3 → 设备 12-15  （端口 7103，独立引擎）

D 节点（005）：8 个 DP rank × 每个 TP2（2 设备协同）= 16 设备
  rank0 → 设备 0,1（端口 7100）…… rank7 → 设备 14,15（端口 7107）
```

**为什么 P 用 TP4、D 用 TP2？** Prefill 是算力活（一次算几万 token），4 卡合力算一个长 prompt 更快；Decode 是带宽/并发活（每步只算 1 个 token，但人多），小 TP + 多 rank = 更多并行引擎、更多席位。这是官方 W8A8 权重的推荐布局。

**"席位"= `--max-num-seqs`**：每个 rank 同时调度的请求数上限。P 每台 4 rank × 16 席 = 64 席；D 8 rank × 72 席 = 576 席（decode 阶段请求停留久，席位要多）。

## Q2：整个部署有多少个流量入口？

| 入口 | 数量 | 谁用 |
| --- | --- | --- |
| **对外业务入口（唯一）** | **1 个：`001:9000` PD 代理** | 客户端/压测只打这里 |
| P 引擎 API | 16 个（4 台 × 7100-7103） | 仅代理内部转发 |
| D 引擎 API | 8 个（005 × 7100-7107） | 仅代理内部转发 |
| Mooncake KV 端口 | P 侧 30000+（每台 4 个）、D 侧 30100+（8 个） | 仅 KV 数据流 |
| DP 协调端口 12321 | 每台 1 个 | 仅引擎启动组网 |

**业务方永远只看见 9000 一个入口**，其余全是内部端口（防火墙只对内网放行即可）。

## Q3：一次请求的完整数据流是怎样的？

以客户端发一个 5000 token 的 prompt 为例：

```
 ①请求
 客户端 ────────────────────────────▶ PD 代理 001:9000
                                        │
                              ② 代理从 16 个 P 端点里挑一个
                                        ▼
                           003:7102 引擎（rank2，设备 8-11，TP4 协同）
                                        │
                              ③ Prefill：5000 token 全部前向计算，
                                 产出这 5000 token 的 KV Cache
                                        │
                              ④ Mooncake KV 传输（:30002 → :3010x）
                                 走 enp23s0f3，几 MB 毫秒级，与计算重叠
                                        ▼
                           005:710x 引擎（TP2）
                                        │  ⑤ 代理把请求转给这个 D 引擎
                              ⑥ Decode：拿着现成 KV 逐 token 生成
                                 （DSpark 投机解码：每步先猜 5 个再验 1 个）
                                        │
                              ⑦ token 流式返回：D → 代理 → 客户端
```

关键点：

- **一个请求的计算被切成两半**：读 prompt 算 KV 在 P，生成在 D。P/D 各只有半段能力，所以不能直连引擎端口，必须代理牵线
- **KV 传输与 prefill 并行**（Mooncake 边算边送），网络不是瓶颈
- **多轮会话**：同一会话再次进入若命中同一 P 的前缀缓存，只增量计算新 token——这是 TTFT 的命脉，也是方案强调"会话粘性"的原因

## Q4：流量怎么选机器？每一跳的决策者是谁？

| 跳 | 谁决策 | 怎么选 |
| --- | --- | --- |
| 客户端 → 代理 | 不用选 | 固定地址 `192.168.0.4:9000` |
| 代理 → 哪台 P | 代理 | 官方示例代理：16 个 P 端点轮询。理想形态（方案 §6.4，生产网关做）：按会话 ID/前缀哈希粘住同一台 P 保命中 |
| P → KV 送到哪个 D | 代理 + 连接器 | 代理把请求转发给选中的 D 端点，Mooncake 连接器按请求 ID 自动配对完成 KV 传输，无需人工指定 |
| 代理 → 哪个 D | 代理 | 8 个 D 端点按活跃序列均衡（D 无前缀缓存，哪台都一样） |
| 引擎 → 用哪几张卡 | 启动时固定 | launcher 预分配（Q1 的设备表），运行期不变 |

**"选机器"全部发生在代理层**，引擎和卡是静态分配的。代理虽只是转发器，却是系统唯一外部依赖点——它挂了业务就断（POC 接受，生产高可用需多实例）。

## Q5：为什么要 PD 分离？放一起混部不是省了通信时间吗？

可以混部（官方 §5.1 就有单机方案），但在本集群的负载画像（200 并发 × 64K-200K 输入 × TTFT/TPOT 双指标）下，**混部省的通信时间远抵不上它引入的干扰代价**。

**先算"通信税"：**

| 上下文 | 单请求 KV | 200Gbps 传输 |
| --- | --- | --- |
| 64K | 57 MB | **2.3 ms** |
| 200K | 178 MB | **7 ms** |

点对点直传、与 prefill 计算重叠——分离的代价是**毫秒级且大部分被隐藏**的。

**再看混部的干扰：** Prefill 是算力型、Decode 是带宽型，混部两者抢同一个调度器——一个 64K prompt 进来 prefill 要算**几秒**，期间所有正在 decode 的用户一步都走不了，TPOT 从 30ms 尖刺到秒级；200 并发下这种尖刺是常态。

> 对比：分离的代价是 2-7ms（隐藏的 KV 传输），混部的代价是秒级 decode 停摆。省的不是时间，是把毫秒的成本换成秒的成本。

**分离的三个额外红利：**

1. **角色化配置极致化**——P：enforce-eager + 前缀缓存 + MegaMoE；D：FULL_DECODE_ONLY 图捕获 + async-scheduling + 重算调度器 + 关缓存。这些配置互斥，混部只能折中
2. **P:D 配比可调**——4P1D 贴长输入；TPOT 硬指标则切 3P2D（方案 §7）。混部焊死 1:1
3. **TTFT/TPOT 独立观测调参**——两侧 `max-num-batched-tokens`（P=8192）与 `max-num-seqs`（D=72）互不牵连

**混部适合的场景**：规模小、负载轻、输入短、追求运维简单——单机就能跑，无需代理与 KV 连接器。

**一句话总结**：PD 分离是用 2ms 可重叠的 KV 传输，换掉秒级的计算互相阻塞，外加两套各自最优的配置和可调配比；输入越长、并发越高，这笔交易越划算。

## Q6：什么是专家并行（EP）？

**把 MoE 模型的全部专家拆开放到多张卡上，每张卡持有其中一部分完整专家。**

先补 MoE 背景：DeepSeek-V4.1-Flash 每层有 **384 个路由专家 + 1 个共享专家**，router 只为每个 token 挑 **top-6** 个专家计算（这就是"激活 8B/16B、总参 552B"的由来）；代价是 384 个专家的权重全部驻留显存（W8A8 下单副本 ~800GB 的大头）。

本部署为 EP16——每台 16 个逻辑设备，每卡持有 384÷16 = **24 个完整专家**。与 DP/TP 对齐着记：

| 并行方式 | 切什么 | 切完之后 |
| --- | --- | --- |
| DP（数据并行） | 切**请求** | 各引擎独立处理不同请求 |
| TP（张量并行） | 切**每层权重矩阵** | 一个矩阵拆 16 份，各卡算小块再拼 |
| **EP（专家并行）** | 切**专家**（专家本身不拆） | 每卡 24 个完整专家，token 按需去找专家所在的卡 |

一个 token 在 MoE 层的旅程：router 算出 6 个目标专家 → **all-to-all dispatch** 把 token 寄给专家所在的卡 → 各卡专家计算 → **all-to-all combine** 寄回并加权合并。

为什么 MoE 用 EP 而不是全 TP：

1. **稀疏激活**：每 token 只用 6/384 专家；TP 切碎每个专家会让 16 卡为 6 个专家空转通信，EP 下无关节的卡可并行算其他 token 的专家——与 DP 天然配合
2. **通信省**：all-to-all 只搬"激活的 token×专家对"
3. **显存布局干净**：专家整存整取

部署体现：P/D 均开 `--enable-expert-parallel`，DP/TP/EP 三种并行同时生效——4 或 8 个 DP rank 各自独立服务请求（DP），rank 内 4 或 2 卡切注意力层（TP），16 卡作为一个 EP 组共同持有全部专家。启动日志 `Dynamic EPLB is False` 表示专家负载均衡用静态均匀分布（压测后发现卡间忙闲不均可再开）。

**一句话总结**：DP 切请求、TP 切注意力层、EP 切专家；EP 让 384 个专家摊满 16 卡，token 靠每层两次机内 all-to-all 找自己的 6 个专家——这也是所有集合通信被按在单机内的原因。

## Q7：什么是 all-to-all？

**一种集体通信模式：每个节点同时给其他所有节点各发一份"不同的"数据**——即"全体同时互寄"，MoE 的 token 找专家天然就是这种通信。

4 卡示意（N 卡则有 N×(N-1) 条并发数据流，16 卡 = 240 条）：

```
发送方向 ↓ / 接收方向 →     卡0      卡1      卡2      卡3
卡0 寄出               →    本地    tokenA   tokenB   tokenC
卡1 寄出               →  tokenD    本地    tokenE   tokenF
卡2 寄出               →  tokenG   tokenH    本地    tokenI
卡3 寄出               →  tokenJ   tokenK   tokenL    本地
```

与其他集体通信对比：

| 模式 | 数据流向 | 典型用途 |
| --- | --- | --- |
| Broadcast | 1 → 所有 | 广播参数 |
| Reduce | 所有 → 1 | 梯度聚合到主卡 |
| All-Reduce | 所有 ↔ 所有（每人拿到**相同结果**） | **TP** 每层拼结果 |
| All-Gather | 所有 ↔ 所有（每人拿到所有人**完整数据**） | 拼分片 |
| **All-to-All** | 所有 ↔ 所有（每人拿到**别人寄给自己的那一小份**，各不相同） | **EP** 分发 token 给专家 |

记忆点：**All-Reduce 是"大家算完汇成同一个数"，All-to-All 是"快递分拣——每人寄出/收到的包裹各不相同"**。

为什么它决定架构选择：decode 每个 step、每一层 MoE 都要 dispatch+combine 两次 all-to-all，一个 step 累计几十次；机内 HCCS 单次微秒级、跨机网卡毫秒级——若跨机，几十次 × 每次多 1ms 直接击穿 TPOT 30ms 预算。**所以 EP 严格限制在单机 16 设备内（HCCS 互联），跨机只留低频的 Mooncake KV 点对点传输。**
